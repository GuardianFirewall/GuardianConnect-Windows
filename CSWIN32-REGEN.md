# CsWin32 — Frozen P/Invoke & Regeneration

The Win32 P/Invoke wrappers are produced by the **CsWin32** source generator
(`Microsoft.Windows.CsWin32`) from a per-project `NativeMethods.txt` list. To
keep the build deterministic and free of on-the-fly generation, that output is
**frozen**: generated once, checked in as static source, and the generator is
**removed from the build**. CI and local builds just compile the checked-in
files — the generator does not run.

## Where the frozen code lives

Each project that uses Win32 interop has its own `Generated/` folder holding the
generated files (one per namespace root: `Windows.Win32.*` + `Windows.Wdk.*`):

- `GuardianConnectSDK/Win32Calls/Generated/`
- `GuardianConnectSDK/Win32Calls.WFP/Generated/`

The files are `<auto-generated>` — do **not** hand-edit them. To change the Win32
surface, edit `NativeMethods.txt` and regenerate (below). Each project also keeps
its `NativeMethods.txt` / `NativeMethods.json` in place as the (now reference-only)
generator input.

Current pinned generator version: **Microsoft.Windows.CsWin32 0.3.298**.

## How generation is disabled

In each project's `.csproj`, the CsWin32 `PackageReference` (and, for
`Win32Calls.WFP`, the `AdditionalFiles` entries) are **commented out** with a
regen note. Because the package is gone, the generator never runs — including in
CI. Kept as a comment (not a live MSBuild toggle) on purpose, so CI can't
accidentally regenerate.

> Note: the CsWin32 package implicitly set `AllowUnsafeBlocks=true`. Where that
> was the only source of it, it is now set explicitly in the `.csproj`
> (e.g. `Win32Calls.WFP`). Leave it — the generated P/Invoke needs unsafe.

Both `Win32Calls` and `Win32Calls.WFP` generate an overlapping `Windows.Win32.*`
surface, so `Win32Calls` suppresses `CS0436` (expected duplicate-type warning
across the two frozen sets). Leave that `NoWarn` in place.

## How to regenerate (periodic update / add an API)

Do this per project you want to update. Example uses `Win32Calls.WFP`;
`Win32Calls` is identical.

1. **Uncomment** the CsWin32 block in the project's `.csproj` (the
   `Microsoft.Windows.CsWin32` `PackageReference`, plus the two `AdditionalFiles`
   for `Win32Calls.WFP`). To move to a newer generator, bump the `Version` here.
2. *(Optional)* edit `NativeMethods.txt` to add/remove APIs.
3. Build with generated-file emission:
   ```
   dotnet build <Project>.csproj -c Release -p:Platform=x64 -p:EmitCompilerGeneratedFiles=true
   ```
4. Copy the emitted `*.g.cs` over the frozen copies:
   ```
   copy obj\x64\Release\net10.0-windows\generated\Microsoft.Windows.CsWin32\Microsoft.Windows.CsWin32.SourceGenerator\*.g.cs  Generated\
   ```
   (`emitSingleFile: true` in `NativeMethods.json` keeps this to one file per
   namespace root.)
5. **Re-comment** the CsWin32 block in the `.csproj`.
6. Clean-build to confirm it compiles from the static files with the generator
   off:
   ```
   rmdir /s /q obj bin
   dotnet build <Project>.csproj -c Release -p:Platform=x64
   ```

If a regenerate changes call-site signatures (as the 0.213 → 0.298 bump did:
`HANDLE` → `FWPM_ENGINE_HANDLE` for WFP, and RAS `RasEnum*` to Span/`ref`/extern
overloads), update the call sites accordingly and re-validate the affected
paths (kill switch, IKEv2 dial enumeration, RAS phonebook cleanup).
